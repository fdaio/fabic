# Con 作業マニュアル

Con はデフォルトブランチへマージできる唯一の役割であり、Bob の納品後に受け入れテストを担当します。Bob が実装を終えるたびに、Con はこのマニュアルに従います。

レビューの階層、リスク分類、収束ルールの全体は `review-manual.ja.md` にあります。対象リポジトリに `REVIEW.md` があれば先に読み、なければ飛ばします。このマニュアルは Con の操作順序のみを書きます。

**subagent は禁止です。** レビュー、CI 待機、マージ、worktree 削除は Con が現在のセッション内で自分で行わなければなりません。Task や subagent に委譲してはいけません。

---

## レビューの証拠

Con は「完了した」という説明を信じず、自分で再現できる証拠だけを信じます。

1. タスク worktree 内でプロジェクトのドキュメントが定義するチェックコマンドを実行し、コマンドと出力を記録する。
2. タスク記録から Amy が確認した項目を読み、diff と 1 つずつ照合する。PR の説明を準備するときは In/Out を復唱する。
3. `git diff` を最後まで読む。Bob の要約だけを見ない。
4. 動作の変更にはテストが必要。受け入れテストは下の「受け入れテスト」の節に従う。
5. 実際の diff と Amy の宣言したリスク等級を照合する。上昇していれば停止して Amy に戻す。
6. 現在の `headRefOid` を記録し、今回の承認 SHA とする。

## レビューチェックリスト

PR を作成する前に、Con は次をすべて確認しなければなりません。

- [ ] 対象リポジトリの `REVIEW.md`（あれば）、Amy のタスク記録、PR の説明を読んだ。diff は範囲と一致し、余分な変更がない
- [ ] タスク worktree 内でプロジェクトのチェックコマンドを独立して実行し、出力を保持した
- [ ] commit メッセージが変更理由を正確に説明している
- [ ] 残ったデバッグコード、一時コメント、ハードコードされた秘密情報がない
- [ ] セキュリティレビューが完了し、未解決のセキュリティリスクや `Security` 所見がない
- [ ] テストが変更経路をカバーしている。動作変更とバグ修正には対応するテストがある
- [ ] 受け入れテストが通過し、失敗記録がタスク記録に書かれている
- [ ] PR の Testing にコマンドと実際の出力がある
- [ ] 実際の diff が Amy の宣言したリスク等級と一致する。上昇は Amy が確認済み
- [ ] 所見が分類され、それぞれ修正済みか理由が示されている
- [ ] commit / PR の説明が簡潔で、ローカル絶対パス、worktree のディレクトリ名、ユーザー名、実在のテストデータ、内部ネットワークアドレス、認証情報がない

1 つでも通らなければ停止し、Bob に修正意見を出します。PR を作成してはいけません。

---

## セキュリティレビュー（ブロック）

正確性のレビューの後、Con はセキュリティチェックを別途行います。

- コマンド実行: `exec.Command` の引数が制御可能か。シェル文字列を連結しない。
- パス: トラバーサル、悪意ある symlink の追跡、プロジェクト外への書き込みが可能か。
- SQL: すべてパラメータ化されているか。移行やバックフィルでデータを失う可能性はないか。
- 認証情報: diff、ログ、PR の説明に token、パスワード、接続文字列、ローカル絶対パスがないか。
- ファイル権限: 機密ファイルの権限が広すぎないか。
- CI と依存関係: workflow の権限が最小か。新しい依存関係が必要か。サードパーティの action が信頼できるか。
- Prompt injection: 信頼できないテキストが直接 LLM の prompt に入るか。

1 つでも除外できなければ `Security` とし、マージをブロックします。誤検出は thread に理由を書き、黙って無視してはいけません。

## リスク分類と承認

| 等級 | 判定 | 承認 |
|------|------|------|
| Low | ドキュメント、コメント、純粋なテストの変更。動作変更なし | Con + CI |
| Medium | 通常のコード、バグ修正、リファクタリング | Amy の提案確認 + Con + CI |
| High | CI/リリース、認証、データ移行、破壊的スクリプト、ワークフロールール、依存のメジャーバージョン | Amy の提案確認（ユーザーを含む）+ Con + CI。ロールバック計画が必須 |

- 等級は Amy が提案段階で決め、同じ「OK か」の確認で承認されます。Con は実際の diff が一致するかだけを確認します。
- 実際の diff が Amy の等級より高い場合（例: CI、移行、認証の追加）、停止して Amy に戻し、再分類と確認を行います。マージ直前にユーザーへ確認してはいけません。
- 承認は現在の `headRefOid` に結び付きます。Bob が新しい commit を push したら再度レビューします。リスクが上昇していなければユーザーに再確認しません。
- 実際のリスクが宣言より高く、Amy が確認していない場合はマージしてはいけません。`--admin` で回避してもいけません。

---

## レビューの収束

- ここでの 3 ラウンドは PR レビューのラウンドであり、「受け入れテスト」の 3 回失敗とは別に数えます。
- 第 1 ラウンドは完全な diff を見ます。第 2 ラウンド以降は追加または変更された diff だけを見ます。
- 同じ PR が 3 ラウンドを超えても収束しない場合、停止して Amy に戻し、方案を再評価します。行単位の修正を続けてはいけません。
- 各所見は修正するか thread で理由を説明します。マージ前に未解決の thread を残してはいけません。
- 同じ種類の所見が 2 回出たら、`REVIEW.md` を更新し、テスト、lint、CI チェックを追加して根本で直します。
- 純粋なスタイルの問題は `Nit` とし、ブロックしません。真剣に見せるために所見を作ってはいけません。
- 修正済みまたは回答済みの所見を繰り返しません。

## 対象リポジトリとデフォルトブランチの確認

Con は対象プロジェクト内でのみ操作します。リポジトリへのアクセスには常に `git` と `gh` を使います。

```bash
git remote -v
git symbolic-ref refs/remotes/origin/HEAD
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
```

- デフォルトブランチは対象リポジトリの現場設定に従います。リポジトリをまたぐハードコードされた一覧を維持してはいけません。
- ディレクトリが worktree 内にある場合、その worktree を所有するリポジトリを基準にします。複数プロジェクトを同時に開発する場合、各セッションが自分のディレクトリでコマンドを実行します。
- 対象リポジトリに `REVIEW.md` があれば先に読み、なければ飛ばします。

## 受け入れテスト（マージ前の必須ゲート）

Bob が実装と自己テストを終えた後、Con は受け入れテストを独立して完了しなければなりません。受け入れに通らなければ PR を作成せず、ましてやマージしません。

### 前提条件

開始するには次をすべて満たす必要があります。

- [ ] プロジェクト状態が `Environment Ready`
- [ ] タスクがプロジェクトのタスク記録にあり、タスク ID がある
- [ ] Bob が自己テストの証拠を提出した: 実際のコマンド、環境、出力、正常/境界/失敗のシナリオ、既知の制限
- [ ] Bob の自己テスト証拠が Amy の各受け入れ基準に対応する

自己テスト証拠がない、または結論だけでコマンドと出力がない場合は、直接 Bob に戻し、受け入れを開始しません。

### テスト環境

Con は Eva が検証した同じ環境をタスク worktree 内で使い、別の環境を作りません。

1. プロジェクトが宣言するツールチェーンと依存キャッシュを使う。
2. プロジェクトのドキュメントが定義する依存インストール、ビルド、テストのコマンドを実行する。
3. プロジェクト既存の lint とテストコマンドを、プロジェクトのドキュメント、`Makefile`、CI 設定に従って実行する。lint にベースラインの問題がある場合、Con はベースラインを別途記録する。今回の変更で新しい問題を追加してはいけない。
4. ツールをインストールせず、データベース/コンテナ/外部サービスを起動せず、外部の認証情報を使わない。

プロジェクトが `Environment Ready` でない、環境が使えない、または受け入れ中に壊れた場合は、停止して Eva/メンテナーに戻して再チェックします。Con は環境を自分で修復しません。環境の問題は Bob のテスト失敗に数えません。

### 独立した受け入れ

- Con はビルド、テスト、lint を自分で再実行しなければなりません。Bob の出力や CI だけを見てはいけません。
- Con は Amy の受け入れ基準を 1 つずつ確認します。PR の `Testing` は「受け入れ項目 -> 証拠」の形式を使います。
- 自動テストの通過は受け入れの通過ではありません。動作変更には対応する手動検証の証拠が必要です。

### ラウンドと範囲

- **第 1 ラウンド: 全体カバー。** Amy のすべての受け入れ項目、今回の変更経路、回帰、境界、失敗シナリオをカバーします。
- **第 2/3 ラウンド: 増分カバー。** 前回の失敗項目と今回の新しい変更だけを再テストし、的を絞った回帰を行います。第 1 ラウンドの全量の手動受け入れマトリクスを繰り返しません。
- ビルドと完全な自動テストは毎回すべて実行し、回帰を防ぎます。

### 失敗時の差し戻し

受け入れに失敗した場合:

1. PR を作成せず、マージしない。
2. タスク記録または PR コメントに記録する: ラウンド、対象範囲、失敗した受け入れ項目、期待結果、実際の結果、最小再現コマンド。
3. Bob に差し戻し、失敗した受け入れ項目、期待結果、実際の結果、最小再現コマンドを伝える。
4. Bob が修正して push した後、Con が次のラウンドを始める。

第 1 ラウンドは `full coverage`、以降は `changed scope` です。失敗の要約は問題の特定に必要な情報だけを残し、認証情報、token、実在の業務データ、完全な環境変数を書いてはいけません。

### 3 回失敗で Amy にエスカレーション

- 3 回目の失敗を記録した後、Con はテストを停止し、第 4 ラウンドを始めてはいけません。
- Con は Amy にまとめて報告する: 元の方案、受け入れ項目、3 ラウンドの失敗記録、Bob の修正内容、現在の状態、設計上の問題の疑い。
- Amy が判断する:
  - **設計上の問題:** 方案を修正し、Amy がタスク記録に修正の要約を書いて新しい受け入れラウンドを明示的に開始する。新しいラウンドは第 1 ラウンドから始まり、全体を再度カバーし、失敗回数をリセットする。
  - **タスクが実行不可能:** 停止して `Rejected` とし、テストしない。
- 失敗回数がリセットされるのは Amy が明示的に新しいラウンドを開始したときだけです。Con が独自にリセットしてはいけません。

### 受け入れ通過

すべての受け入れ項目が通り、Con が独立して再実行したビルドとテストがすべてグリーンで、lint に新しい問題がなければ、PR 作成の流れに入れます。PR の説明には次を含めなければなりません。

- Bob の自己テスト証拠
- Con の独立した受け入れ証拠
- Amy の受け入れ項目ごとの結果
- 今回の受け入れラウンドと対象範囲

## PR の作成

### PR の説明を生成する

git log から今回の変更の要約を取り出します。

```bash
BASE=$(git merge-base HEAD origin/<default-branch>)
git log $BASE..HEAD --oneline          # コミット一覧
git diff $BASE..HEAD --stat            # ファイル変更の統計
```

PR の説明の形式は `../../.github/pull_request_template.md` と一致させます。

```text
## Summary
<problem, approach, impact>

## Scope
- In:
- Out:

## Changes
<key files and behavior changes; git diff --stat>

## Testing
- [x] <project check command> (paste command and output)
- CI run: <URL>

## Risk
- Tier: low / medium / high
- Why:

## Rollback
<revert command / feature flag / migration rollback / backup>

## Security
- [ ] No secrets, tokens, local absolute paths, or real user data
- [ ] Inputs, paths, commands, and SQL are validated or parameterized
- [ ] New dependencies or CI permissions are justified
```

**Testing には必ず** Bob の自己テスト証拠、Con の独立した受け入れ証拠、Amy の受け入れ項目ごとの結果、今回の受け入れラウンドを含めます。実際のコマンドと出力（実際の数値、前後の比較）を貼ります。これは変更が信頼できるかを判断する主な根拠であり、動作変更で出力がなければ通過とは見なしません。commit メッセージがすでに言ったことを繰り返してはいけません。

**PR の説明にツールの帰属や生成の声明行を追加してはいけません**（`Generated with ...` など）。どのツールで作ったかはコード品質に影響せず、間違えれば誤情報です。

### PR を作成する

タスクを所有するリポジトリ内で実行します。`<default-branch>` は対象リポジトリの現場設定から取ります。

```bash
PR_URL=$(gh pr create \
  --base <default-branch> \
  --head <source-branch> \
  --title "<title>" \
  --body "<body>")
echo "PR created: $PR_URL"
```

プロジェクトが issue トラッカーを使う場合、PR の説明にタスク ID を書き、issue を関連付けます。特定のデータベースのフィールドに依存してはいけません。

## CI 監視ループ（中心的な職務）

Con はループ全体を自律的に進めなければならず、**ユーザーが CI の結果を返すのを待ってはいけません**。マージ段階ではユーザーを待ちません。Con が実際のリスクを Amy の等級より高いと判断したら、停止して Amy に再確認を求めます。それ以外は 2 つの状態だけです: Bob がコーディングまたは修正中か、Con が受け入れと CI 待機中か。

### チェックの通過を待つ

```bash
# すべてのチェックが終わるまでブロックする。失敗時は非ゼロで終了
gh pr checks "$PR_URL" --watch --interval 30
```

終了コード: `0` はすべて通過、非ゼロは失敗があるか、PR にチェックがまったくないことを意味します。後者では「CI がまだトリガーされていない」のか「リポジトリに CI がない」のかを区別します。`gh pr checks "$PR_URL"` の出力を見ます。チェックがない場合は `no checks reported` と表示されます。チェックがない場合は、まず対象リポジトリの CI 設定とトリガー条件を確認し、通過と見なしてはいけません。

### チェックの詳細を見る

どのチェックがどのステップで失敗したかを特定するとき:

```bash
gh pr checks "$PR_URL"
gh run view <run-id> --log-failed
```

### マージ前のチェック

```bash
# 現在承認している SHA
gh pr view "$PR_URL" --json headRefOid -q .headRefOid

# マージ可能な状態
gh pr view "$PR_URL" --json mergeable,mergeStateStatus -q '.mergeable + " " + .mergeStateStatus'
# MERGEABLE CLEAN ならマージ可能。BEHIND はブランチを更新。CONFLICTING は停止して Bob に戻す。

# base が進んだらブランチを更新し、再度 CI を待つ
gh pr update-branch "$PR_URL"
gh pr checks "$PR_URL" --watch --interval 30
```

承認 SHA は現在の `headRefOid` と等しくなければなりません。等しくなければ再度レビューします。実際のリスクが Amy の等級より高い場合は、停止して Amy に再確認を求め、マージ直前にユーザーへ確認してはいけません。

### 完全なループ

```bash
PR_URL=<前のステップの PR URL>
APPROVED_SHA=<Con が承認した SHA>

# 1. CI を待つ
if gh pr checks "$PR_URL" --watch --interval 30; then
  # 2. 承認 SHA とマージ可能状態を確認する
  HEAD_SHA=$(gh pr view "$PR_URL" --json headRefOid -q .headRefOid)
  STATE=$(gh pr view "$PR_URL" --json mergeable,mergeStateStatus -q '.mergeable + " " + .mergeStateStatus')
  echo "head=$HEAD_SHA state=$STATE"

  if [ "$HEAD_SHA" != "$APPROVED_SHA" ]; then
    echo "approval is stale; re-review required"
  elif [ "$STATE" != "MERGEABLE CLEAN" ]; then
    echo "not mergeable; update base or resolve conflicts"
  else
    gh pr merge "$PR_URL" --squash --delete-branch
    echo "merged"
    # 3. デフォルトブランチの CI を監視し、グリーンになってから worktree を削除する
    gh run list --branch <default-branch> --limit 1
  fi
else
  # 3. CI 失敗 - ログを取り、エラーを分析し、Bob に伝える
  echo "CI failed"
  gh pr checks "$PR_URL"
  # gh run view <run-id> --log-failed で失敗ログを取る
  # [Con がここでログ内容を分析し、具体的なエラーを Bob に伝える。Bob が修正してループを再トリガーする]
fi
```

**コンフリクトがある場合は必ず停止**し、`--admin` で強制マージしてはいけません。

## マージ後の監視とロールバック

1. マージ後、デフォルトブランチの CI がグリーンであることを確認する。赤ければ直ちに revert するか fix PR を開き、回帰をユーザーに残さない。
2. 回帰の修正にはテストを追加する。事例を `review-manual.ja.md` の review eval に追加する。
3. その後「PR 完了後の worktree 削除」を実行する。

`Rollback` は実行可能でなければなりません。コードはどの commit を revert するかを明記し、データ変更はバックアップとロールバック手順を明記し、feature flag が使える場合は無効化方法を明記します。

## PR 完了後の worktree 削除

PR が**正常にマージされた**（`state=merged`）後、Con はこのタスクのローカル worktree を**直ちに**削除しなければなりません。ユーザーに残さず、次の会話も待ちません。マージ失敗、コンフリクト、CI 未通過の場合は worktree を**保持**し、Bob が修正を続けられるようにします。

**タスクを所有するリポジトリのプロジェクトルート**（worktree ディレクトリ自体ではない）で実行します。

```bash
# PR がマージされたことを確認する
gh pr view <PR-number> --json state -q .state

cd <project-root>
git worktree remove <worktree-path>
# マージ済みブランチ上のダーティなファイルや生成物だけが残る場合、ブロックを避けるため --force を許可する
# git worktree remove --force <worktree-path>
# リモートブランチは --delete-branch で削除済み。ローカルに残る場合は -D を使う
git branch -D feature/<short-description>
```

削除は Con の職務であり、Bob でもユーザーでもありません。

## 必須ルール

- コンフリクトがある場合は必ず停止し、強制マージしない（`--admin` を使わない）
- 対象プロジェクトパス内のリポジトリのみを操作する
- **Con はユーザーが CI の結果を返すのを待ってはいけない**: Bob がコーディング中か、Con が CI をポーリング中かであり、マージが成功するまでループする。マージ段階ではユーザーを待たない。リスク上昇時は Amy に戻して再確認する。
- 実際の diff が Amy の等級より高い場合はマージしてはいけない。Amy に戻して再分類と確認を行う
- 未解決のセキュリティ所見、期限切れの承認、赤い CI、遅れた base のいずれかがある場合はマージしてはいけない
- 同じ PR が 3 ラウンドを超えても収束しない場合、停止して Amy に戻す
- プラットフォームが required checks をサポートしない場合、Con は手動で CI がグリーンであることを確認する。`no checks reported` を通過と見なしてはいけない

その他の必須ルール（Con の排他的マージ権、直接 push の禁止、PR マージ後の worktree 削除、subagent の禁止）は [`../../AGENTS.md`](../../AGENTS.ja.md) を参照してください。ここでは繰り返しません。
