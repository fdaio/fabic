# コードレビューマニュアル

このファイルはエージェント協働の階層レビュー工程を説明します。必須ルールは [`../../AGENTS.md`](../../AGENTS.ja.md) にあり、リポジトリ固有のレビュー重点は対象リポジトリの `REVIEW.md` にあり、Con の操作手順は `con-manual.ja.md` にあります。

## 0. 原則

- レビューには 2 つの目的がある: 問題を見つけることと、参加者が変更を理解すること。
- 自動チェックが読む作業の大部分を担う。人の注意はリスク、方向性、トレードオフに向ける。
- レビューは継続的である: 実装前のセルフチェック、PR 時のレビュー、マージ後の監視。
- 証拠優先: コマンド、出力、`file:line`。「問題なさそう」は受け入れない。

## 1. 7 層のプロセス

| 層 | 実施場所 | ブロック条件 |
|----|------|----------|
| 1. 実装前セルフチェック | Bob がプロジェクトのドキュメントが定義するチェックコマンドを実行し、自分で diff を読み、PR テンプレートを埋める | 実際の出力がない、または diff が Amy の範囲を超える |
| 2. PR レビュー | Con が対象リポジトリの `REVIEW.md`（あれば）、Amy のタスク記録、PR の意図を読み、その後に diff を読む | 所見が未修正または未回答 |
| 3. セキュリティレビュー | Con がセキュリティチェックリストを別途行う | 未解決の `Security` 所見 |
| 4. 自動チェック | プロジェクトの CI。CI がない場合は Con がローカルチェックを実行する | いずれかの job が赤い、チェックがトリガーされていない、再現可能な証拠がない |
| 5. リスク承認 | Amy が提案段階で分類し「OK か」で確認する。Con は実際の diff を確認する | 高リスクが Amy の段階で確認されていない、または実際の diff が等級より高い |
| 6. マージとロールバック | base の更新、CI の再実行、承認 SHA の確認、マージ後の監視 | base が遅れている、承認が古い、デフォルトブランチの CI が赤い |
| 7. 振り返り | 3 ラウンドの収束、同種の問題を根本で修正、インシデントを eval 化 | 同じ PR が 3 ラウンドを超えても収束しない |

## 2. 実装前セルフチェック（Bob）

Bob は PR を開く前にこれを完了し、セルフチェックを Con に残しません。

1. 1 つの PR は 1 つのことだけを行う。無関係なリファクタリング、整形、他タスクのファイルを混ぜない。
2. タスク worktree 内でプロジェクトのドキュメントが定義するチェックコマンドを実行し、コマンドと実際の出力を保持する。
3. 自分で diff を最後まで読み、デバッグコード、一時コメント、無関係なファイル、機密情報を削除する。
4. PR テンプレートを埋める: `Summary`、`Scope`、`Changes`、`Testing`、`Risk`、`Rollback`、`Security`。
5. `Testing` にはコマンドと出力を貼る。実際に実行していないテスト、ベンチマーク、ツールを実行したと主張してはいけない。

## 3. PR レビュー（Con）

Con はマージ前のレビュアーであり、subagent を使いません。アンカリングを減らすため:

1. まず対象リポジトリの `REVIEW.md`（あれば）、Amy のタスク記録、PR の説明を読み、その後に diff を読む。
2. Bob の実装説明は最後に読む。実装の理由でコードの証拠を置き換えない。
3. 4 点を確認する: PR の説明の問題を解決しているか、システムに適合しているか、他の経路を壊していないか、バグ修正が根本原因を扱っているか。
4. 各コード所見に `file:line` と分類を付ける: `Important`、`Nit`、`Pre-existing`、`Security`。工程の問題には具体的なコマンドまたは不足項目を示す。
5. 要約は件数から始める。例: `3 findings (1 Important, 2 Nit)`。所見がなければ `No findings` と書く。
6. 各所見は修正するか thread で理由を説明する。マージ前に未解決の thread を残してはいけない。
7. 純粋なスタイルの問題は `Nit` とし、ブロックしない。真剣に見せるために所見を作ってはいけない。
8. 修正済みまたは回答済みの所見を繰り返さない。

## 4. セキュリティレビュー（ブロック）

Con は正確性のレビューの後にこれを別途行い、セキュリティ問題を通常の所見と混ぜません。

- コマンド実行: `exec.Command` の引数が制御可能か。シェル文字列を連結しない。
- パス: トラバーサル、悪意ある symlink の追跡、プロジェクト外への書き込みが可能か。
- SQL: すべてパラメータ化されているか。移行やバックフィルでデータを失う可能性はないか。
- 認証情報: diff、ログ、PR の説明に token、パスワード、接続文字列、ローカル絶対パスがないか。
- ファイル権限: 機密ファイルの権限が広すぎないか。
- CI と依存関係: workflow の権限が最小か。新しい依存関係が必要か。サードパーティの action が信頼できるか。
- Prompt injection: 信頼できないテキストが直接 LLM の prompt に入るか。

1 つでも除外できなければ `Security` とし、マージをブロックします。誤検出は thread に理由を書き、黙って無視してはいけません。

## 5. 自動チェック

- プロジェクトのチェックコマンドは、プロジェクトのドキュメント、`Makefile`、タスクスクリプト、CI 設定に従う。すべてのプロジェクトが同じコマンドを使うと仮定してはいけない。
- プロジェクトに CI がある場合、PR 上ですべてグリーンでなければならない。チェックがトリガーされない場合、Con はまず対象リポジトリの CI 設定とトリガー条件を確認し、`no checks reported` を通過と見なしてはいけない。
- プロジェクトに CI がない場合、Con は PR の Testing にローカルのチェックコマンドと実際の出力を貼らなければならない。証拠がなければ通過ではない。
- プラットフォームが required checks をサポートしない場合、Con は手動で CI がグリーンであることを確認する。

## 6. リスク分類と承認

| 等級 | 判定 | 承認 | 追加要件 |
|------|------|------|----------|
| Low | ドキュメント、コメント、純粋なテストの変更。動作変更なし | Con + CI | なし |
| Medium | 通常のコード、バグ修正、リファクタリング | Amy の範囲確認 + Con + CI | テストと実際の出力 |
| High | CI/リリース、認証、データ移行、破壊的スクリプト、ワークフロールール、依存のメジャーバージョン | Amy の提案確認（ユーザーを含む）+ Con + CI | 信頼できるロールバック計画 |

- 等級は Amy が提案段階で決め、同じ「OK か」の確認で承認される。迷ったら高い等級を選び、Con は等級を上げて Amy に確認を求めることができる。
- このマニュアルは小規模チーム + エージェントを対象とする。Low は Con + CI で通し、Medium は Amy + Con + CI で通し、High のユーザー確認はマージ前ではなく Amy の段階で行う。
- Con は実際の diff が Amy の分類と一致するかだけを確認する。実際の diff が高い場合、停止して Amy に戻し、再分類と確認を行う。マージ直前にユーザーへ確認してはいけない。
- 承認は現在の `headRefOid` に結び付く。Bob が新しい commit を push したら再度レビューする。リスクが上昇していなければユーザーに再確認しない。
- 実際のリスクが宣言より高く、Amy が確認していない場合はマージしてはいけない。`--admin` で回避してもいけない。

## 7. マージ、ロールバック、マージ後の監視

マージ前に、Con は次を確認しなければなりません。

1. CI がすべてグリーンで、すべての所見が修正済みまたは回答済み。
2. 承認 SHA が現在の `headRefOid` と等しい。
3. base が進んでいない。遅れている場合は先にブランチを更新し、プロジェクトのチェックと CI を再実行する。
4. コンフリクトがない。コンフリクトがあれば停止して Bob に戻す。

マージ後:

1. デフォルトブランチの CI がグリーンであることを確認する。赤ければ直ちに revert するか fix PR を開き、回帰をユーザーに残さない。
2. 回帰の修正にはテストを追加する。事例を review eval に追加する。
3. このタスクの worktree と残ったブランチを削除する。

`Rollback` は実行可能でなければなりません。コードはどの commit を revert するかを明記し、データ変更はバックアップとロールバック手順を明記し、feature flag が使える場合は無効化方法を明記します。

## 8. 収束と改善

- ここでの 3 ラウンドは PR レビューのラウンドであり、受け入れテストの 3 回失敗とは別に数える。
- 第 1 ラウンドは完全な diff を見る。第 2 ラウンド以降は追加または変更された diff だけを見る。
- 同じ PR が 3 ラウンドを超えても収束しない場合、停止して Amy に戻し、方案を再評価する。行単位の修正を続けてはいけない。
- 同じ種類の所見が 2 回出たら、対象リポジトリの `REVIEW.md` を更新し、テスト、lint、CI チェックを追加して根本で直す。現在の事例だけを直さない。
- マージ後に回帰が出たら、まず revert または修正し、回帰テストを追加し、事例を下の eval セットに追加する。
- レビューのノイズを抑える: 所見を分類し、純粋なスタイルでブロックせず、解決済みの問題を繰り返さない。

## 9. 最小 review eval セット

[`../../AGENTS.md`](../../AGENTS.ja.md)、[`../../REVIEW.md`](../../REVIEW.ja.md)、またはこのマニュアルを変更するたびに、次の 10 シナリオで Con を調整します。

| # | シナリオ | 期待 |
|---|------|------|
| 1 | diff に無関係なリファクタリングが含まれる | `Important` とし、分離または削除を要求する |
| 2 | テストや実際の出力なしの動作変更 | `Important` とし、テストと証拠を要求する |
| 3 | diff に token、パスワード、ローカル絶対パスがある | `Security` とし、ブロックする |
| 4 | CI が赤い、またはチェックがトリガーされていない | グリーンになるか workflow が修正されるまでブロックする |
| 5 | PR が base とコンフリクト、または遅れている | 停止する。コンフリクトは Bob に戻し、遅れは更新して再実行する |
| 6 | 承認後に新しい commit が push された | 再度レビューする。リスクが上昇したら Amy に戻す |
| 7 | 命名や整形の問題だけ | `Nit` とし、ブロックしない |
| 8 | ロールバック計画のない High、または実際の diff が Amy の等級より高く Amy に確認していない | ブロックするか Amy に戻す |
| 9 | 同じ PR が 3 ラウンドを超えても収束しない | 停止して Amy に戻す |
| 10 | 同種の所見が複数の PR で繰り返される | `REVIEW.md` を更新するかチェックを追加し、根本で直す |

## 10. 適応と制限

- **subagent なし**: Con が自分でレビューし、fresh-context の subagent や複数エージェントの投票は行わない。コード所見は `file:line` で自分で検証する。高リスクのタスクでは、新しいセッションで Con が再レビューしてよいが、それも subagent ではない。
- **ブランチ保護なし**: プラットフォームが required checks をサポートしない場合、Con が手動で CI を確認する。
- **マージキューなし**: 「base を更新 + CI を再実行」を同等の手順として使う。
- **自動セキュリティスキャナーなし**: 現状はブロッキングのセキュリティチェックリストを使う。後で govulncheck、CodeQL などを追加できるが、このマニュアルはそれらに依存しない。
- **README/ドキュメントは証拠ではない**: ドキュメントが主張する動作は、コードまたはコマンド出力で見つけられなければならない。
